# Live Wikimedia synchronization smoke test

## Method

On 2026-11-10, the actual `WikiClient` and `SyncWorker` were run against `simple.wikipedia.org` with the configured WekI bot User-Agent, concurrency 1, a 1-second request delay, one-page fetch cap, and one retry. Each run used a disposable SQLite database. The test read only public API data and wrote only to that temporary database.

To keep listing bounded, the initial run queried a 10-minute UTC interval and the incremental run queried the immediately following 5-minute interval. The test did not backfill from a production ZIM date or perform a full wiki synchronization.

## Results

| Run | UTC window | Fetched | Final overlay counts | Cursor / result |
| --- | --- | ---: | --- | --- |
| Initial listing with no cursor | 00:00–00:10 | 1 | 0 articles, 0 deletions, 1 redirect, 4 backlog items | `00:10`, `ok` |
| Incremental listing | 00:10–00:15 | 1 | 1 article, 0 deletions, 1 redirect, 8 backlog items | `00:15`, `ok` |

Both runs reported zero failed fetches. The initial fetch stored a redirect; the incremental run stored an article. SQLite `PRAGMA integrity_check` returned `ok`. The temporary database was removed when the test finished.

A separate short live incremental run used a recent five-minute window, fetched one page, recorded one redirect, and finished with `last_result=ok` and integrity `ok`.

## Scope and limitations

This verifies the current Action API/REST API request path, response parsing, backlog/cursor persistence, one redirect, and one article fetch against the real service. It is not a full initial sync or representative throughput test. No deletion, move, restore, rate limit, server-provided retry delay, network interruption, or duplicate-revision event occurred in these short windows; those cases remain covered by mocked tests only. No live write or edit request was sent.
