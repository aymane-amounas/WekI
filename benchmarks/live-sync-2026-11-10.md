# Live Wikimedia synchronization smoke test

## Method

On 2026-11-10 I ran the actual `WikiClient` and `SyncWorker` against `simple.wikipedia.org` with the configured WekI bot User-Agent, concurrency 1, a 1-second request delay, a one-page fetch cap, and one retry. Each run used a throwaway SQLite database. The test only read public API data and only wrote to that temporary database.

To keep the listing bounded, the initial run queried a 10-minute UTC interval and the incremental run queried the 5-minute interval right after it. The test did not backfill from a production ZIM date or do a full wiki sync.

## Results

| Run | UTC window | Fetched | Final overlay counts | Cursor / result |
| --- | --- | ---: | --- | --- |
| Initial listing with no cursor | 00:00–00:10 | 1 | 0 articles, 0 deletions, 1 redirect, 4 backlog items | `00:10`, `ok` |
| Incremental listing | 00:10–00:15 | 1 | 1 article, 0 deletions, 1 redirect, 8 backlog items | `00:15`, `ok` |

Both runs reported zero failed fetches. The initial fetch stored a redirect; the incremental run stored an article. SQLite `PRAGMA integrity_check` came back `ok`. The temporary database was removed when the test finished.

A separate short live incremental run used a recent five-minute window, fetched one page, recorded one redirect, and finished with `last_result=ok` and integrity `ok`.

## Scope and limitations

What this proves is narrow but real: the current Action API and REST request path, the response parsing, backlog and cursor persistence, one redirect, and one article fetch all work against the live service. It's not a full initial sync and not a representative throughput test. No deletion, move, restore, rate limit, server-provided retry delay, network interruption, or duplicate-revision event happened in these short windows, so those cases are still only covered by mocked tests. No live write or edit request was ever sent.
